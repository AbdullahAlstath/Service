SW 7.1 – GUI Frozen and Unresponsive

MKS 1849332

Summary:

XE3 - 7.1.5.4 - BIOS correct, customer experiencing intermittent

Identification #1:

Similar to MKS# 1849332

It looks like it happened during sample rack loading. Maybe we can ask the customer to ensure that pop-up dialogs are dealt with correctly.

2020-10-23 06:43:47,377 Navigate[1217]: UI_Activity Main screen switched to SampleRackLoad

2020-10-23 06:43:47,377 PrepareForDisplay[65]: UI_Activity RichTextConfirm dialog activated, text: <u>To correct Patient Sample unreadable barcodes:</u><br/>

  1. Select OK to exit.

  2. Remove Sample Rack from the bay.

  3. Check sample barcode to ensure it is facing the scanner. Adjust as needed.

  4. If barcode is damaged or unreadable:

    • Use the handheld scanner to scan the tube position barcode on the rack.
    • Use the handheld scanner or the keyboard to enter the sample barcode ID.

  5. Upon completion of barcode correction, load the Sample Rack back into the original lane.

If EQC is unlabeled:

  1. Select OK to exit
  2. Select the message in the Status column
  3. Select the Assign EQC button to assign a name to the unlabeled EQC

2020-10-23 06:43:47,377 Show[151]: UI_Activity Modal dialog activated: GenProbe.Panther.UI.SubPages.RichTextConfirmPage ß Modal dialog popped up

2020-10-23 06:43:56,028 Navigate[1217]: UI_Activity Main screen switched to SampleRackBay ß System switched to another page, hiding the dialog

Workaround/Recommendation:

*Customer to ensure that pop-up dialogs are dealt with correctly.

*If they have samples running, they can let the system continue to run until finished. No need to shut it down until everything finishes processing. The UI should still be updating itself so they should be able to see the instrument state

*Restart GUIGraphical User Interface – allows users to interact with the software using images, graphical icons, and visual indicators rather than text commands., Quick press on the power button is the best option. That will at least do a semi-safe shutdown. Holding the power button would be last resort.

Identification #2:

Customer attempted to pull several reports, and when they did the PC locked up for over an hour, then crashed.

This one looks like a previously reported issue. MKS# 2216042 covers it.

The UI status can be gauged by looking for the ticks that are logged every second. Below is the last tick from the UI, indicating that it is unresponsive from this point forward.

2021-01-13 16:44:31,333 periodicTimer_Tick[2022]: Tick

The last UI activity I can see they were on the Results screen.

2021-01-13 16:43:34,332 Navigate[1217]: UI_Activity Main screen switched to Results

This is the first exception. Almost exactly an hour after the last tick, we see an exception from the UI. This is the one-hour timeout that is configured for threads in our system.

2021-01-13 17:44:31,693 Software exception occurred [406.001.00001]

2021-01-13 17:44:31,693 Exception caught by UI: Operation Timeout: ResultPage.ResultProvider.ChangeHandlerDM (c:149,s:118)(Running) TD:01:00:00.0006512 RD:01:00:00.0006512 TO:01:00:00(True) CD:00:00:00, trace: [406.001.00002]

The two items that point to 2216042 are the fact that they were last at the Results screen and the ResultPage.ResultProvider.ChangeHandlerDM exception that occurred almost exactly an hour later.

Resolution:

This would be more a monitoring situation if it keeps occurring. It should be a fairly rare defect, and unfortunately, no workaround.
