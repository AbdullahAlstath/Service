Dilution factor

Panther will apply a "DIL" dilution comment to an undiluted result if a diluted test order is ordered for the same SID while the original test order is processing.

Scenario is:

1) Operator removes sample tube after initial test was in process

2) Diluted sample

3) Reloaded dilute sample

4) Created replicate of the initial test

Operator must name the diluted replicate with an SID different from the initial undiluted replicate to avoid this problem.

2651372

LIS results

Panther is incorrectly sending results to the LIS that contain "<96>" in the comment field. Most LIS try to convert "<96>" into a symbol which causes the checksum to fail because Panther is counting them as individual characters.

Seen so far with results for the LDT-SARS-CoV-2 (SARS PCR) and GBS assays.

No workaround at this time in Panther. SW is looking into the issue.

Instruct customers/LIS that they will need to have the LIS treat "<96>" as for individual characters and not convert to a symbol.

Example: <- 1C|5|I|^icrfu <96> IC is negative.|I<CR>B1<CR><LF>

ASTMAmerican Society for Testing and Materials (ASTM) is an international standards organization that develops and publishes voluntary technical standards. 1381/1394 Logs: “<- 1C|5|I|^icrfu <96> IC is negative.|I<CR>B1<CR><LF>

2285407

Password

A customer reported that every time they logged into an instrument at their site, they were prompted to reset their password. It was determined that this is related to Panther Link, which shares operator account information with all instruments in the same Data Sharing Group.

This is a defect that occurs when the expiration of a password is set to 0. When the user sets this value to 0 the data is shared to other instruments with a null value for the expiration. The receiving instruments see this null value and because of the defect, set the expiration to the current time. Requiring the user to go to each instrument and update the password.

The workaround is to ensure the expiration of a user’s password is never set to 0.

2472203

Plus Fluids

Customer reported that both of the universal fluid kits (A&B) were marked as In Use long after one of the kits should have no longer been In Use. Customer is not able to change either of the fluid kits during assay processing because both are In Use.

This is a rare issue that can only occur in a very specific timeframe when SW is scheduling the disposal of a leading prime MTU at the same time waste unload (during assay processing) is happening. In this situation it is possible that the disposal of the lead prime MTU is skipped and this results in the empty fluid kit remaining in the ‘in use’ state. Unfortunately when this occurs the empty fluid kit is unable to be replaced. There is no workaround for this once it occurs. The operator will have to wait until processing has completed before that kit can be replaced. This issue can occur in both 7.1 and 7.2 SW. The anomaly has been scheduled to be fixed in v7.4 software

No workaround at this time.

UFP.EvaluateInUseKitsLocation (tells you which fluid kits are currently In Use)

UFM.IsKitValid (tells you the RTR and RTP for each bottle in a fluid kit)

2257770

Screen Frozen

Software freezes when starting PC reboot maintenance. This does not happen every time in 7.2.1. This most often occurs when there are still MTUs in the OQ that need disposal. If enough time has passed since priming or Assay Processing has completed then this issue should not occur.

The customer should wait it out if their system hangs during a reboot. In most cases the system will continue with the reboot after ~15 minutes.

If customer does not want to wait or if it's been > 15 min you can try to use the keyboard to shut down instrument from GUI.

2287291/ 2321800

Software exception

Customer likely recently completed a PC reboot, and a message will read "Assay reagent racks are located in different lane positions after the maintenance reboot. Reagent kits need to be reloaded to confirm kit information". If the operator ignores this message and proceeds with loading different kits, SW exception errors may pop up and/or incorrect ML# can be assigned to a worklist if it is the same assay/same lane, but different LN.

The workaround is to ensure customer does not load or unload reagents during a maintenance reboot, as instructed in the Ops Manual. To clear the error, customer can unload all racks and restart.

If customer runs into this again:

  1. Remind operator and site of proper process when “Allow Reagents to remain loaded during Maintenance Restart” is enabled.
  2. Clear error, unload all racks and restart instrument.

Another fix is upgrading to v7.2.5.

2467984

Worklist

A reagent kit used on day one was removed but samples run the next day were on the original WL from day one.

  • The anomaly is related to the Allow Reagents to Remain Loaded During Maintenance Restart feature and can only happen on systems that have this feature enabled.
  • Only TMA kits that were left onboard through a maintenance restart could be impacted.
  • Issue is not tied to the samples themselves so any impacted samples can be safely retested.
  • SW Dev was unable to identify a way to prevent this from happening though fortunately this error has proven to be rare.

This could be avoided by disabling the ‘allow reagents to remain loaded’ configuration but this issue is so uncommon, and the benefit to having this configuration enabled is so great, that it’s not worth it. So my recommendation would be to continue to use the system as intended. There is still a risk that this could happen but the chances so remote that it’s not worth the cost to avoid.
